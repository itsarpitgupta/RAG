RAG with Persistent Memory Using LangGraph¶

In real-world applications, Retrieval-Augmented Generation (RAG) cannot operate in isolation. Users ask multi-turn questions, reference earlier answers with pronouns ("Can you explain the second point?" or "How does that compare?"), and expect the assistant to remember previous context.

This notebook implements RAG with Persistent State & Memory using LangGraph Checkpointing (MemorySaver) and MessagesState.

Key Architectural Features¶

  • Thread-Scoped Memory: State checkpoints are keyed by thread_id, enabling isolated, independent multi-user sessions.
  • Tool-Aware Decisions: The LLM autonomously determines whether external knowledge retrieval is necessary or if it can answer conversational queries directly.
  • End-to-End Context Grounding: The generation step synthesizes answers combining the retrieved context chunks and the multi-turn dialogue history.
  • ReAct Agent Integration: Demonstrates both custom LangGraph StateGraph orchestration and prebuilt create_react_agent with checkpointers.

from langchain_core.tools import tool

@tool
def retrieve(query: str) -> str:
    """Retrieve information related to the query from the internal knowledge base."""
    retrieved_docs = vector_store.similarity_search(query, k=2)
    serialized = '\n\n'.join(
        f'Source: {doc.metadata}\nContent: {doc.page_content}'
        for doc in retrieved_docs
    )
    return serialized

Step 5: Define LangGraph Workflow Nodes¶
We define the three core nodes that govern the RAG cycle:


    

  1. query_or_respond: The LLM is bound to the retrieve tool. It inspects the dialogue history and decides whether to output a tool call (to search FAISS) or answer directly.
    2. 

  2. tools: ToolNode([retrieve]) executes the tool call and returns the retrieved documents as a ToolMessage.
    3. 

  3. generate: Synthesizes a grounded, concise answer using both retrieved tool results and the ongoing conversation history.
    4. 



















In [6]:






from langchain_core.messages import SystemMessage
from langgraph.graph import MessagesState
from langgraph.prebuilt import ToolNode

# Node 1: Decide whether to call the retrieval tool or reply directly
def query_or_respond(state: MessagesState):
    """Generate tool call for retrieval or respond directly."""
    llm_with_tools = llm.bind_tools([retrieve])
    response = llm_with_tools.invoke(state['messages'])
    return {'messages': [response]}

# Node 2: Tool execution node
tools = ToolNode([retrieve])

# Node 3: Grounded generation node
def generate(state: MessagesState):
    """Generate grounded answer using retrieved context and conversation history."""
    # Extract tool messages from recent steps
    recent_tool_messages = []
    for message in reversed(state['messages']):
        if message.type == 'tool':
            recent_tool_messages.append(message)
        else:
            break
    tool_messages = recent_tool_messages[::-1]

    # Format retrieved context into system prompt
    docs_content = '\n\n'.join(doc.content for doc in tool_messages)
    system_message_content = (
        'You are an assistant for question-answering tasks. '
        'Use the following pieces of retrieved context to answer '
        'the question. If you do not know the answer, say that you '
        'do not know. Use three sentences maximum and keep the '
        'answer concise.\n\n'
        f'{docs_content}'
    )

    # Filter out redundant intermediate tool calls from LLM input
    conversation_messages = [
        message
        for message in state['messages']
        if message.type in ('human', 'system')
        or (message.type == 'ai' and not message.tool_calls)
    ]
    prompt = [SystemMessage(content=system_message_content)] + conversation_messages

    response = llm.invoke(prompt)
    return {'messages': [response]}

print('LangGraph nodes defined successfully.')

Step 6: Assemble and Compile the Graph with Persistent Memory¶
We construct the StateGraph(MessagesState), wire the conditional edge using tools_condition, and attach a MemorySaver checkpointer.


    

  • MemorySaver: Stores conversation checkpoints in-memory keyed by thread_id.
    • 

  • tools_condition: Automatically routes to 'tools' if the LLM produced a tool call, or END if it produced a direct conversational response.
    • 



















In [7]:






from langgraph.graph import END, StateGraph
from langgraph.prebuilt import tools_condition
from langgraph.checkpoint.memory import MemorySaver
from IPython.display import Image, display

# Initialize graph builder with MessagesState schema
graph_builder = StateGraph(MessagesState)

# Add nodes
graph_builder.add_node('query_or_respond', query_or_respond)
graph_builder.add_node('tools', tools)
graph_builder.add_node('generate', generate)

# Set entry point and routing edges
graph_builder.set_entry_point('query_or_respond')
graph_builder.add_conditional_edges(
    'query_or_respond',
    tools_condition,
    {END: END, 'tools': 'tools'},
)
graph_builder.add_edge('tools', 'generate')
graph_builder.add_edge('generate', END)

# Attach in-memory checkpointer
memory = MemorySaver()
graph = graph_builder.compile(checkpointer=memory)

print('LangGraph RAG workflow with persistent memory compiled successfully!\n')
display(Image(graph.get_graph().draw_mermaid_png()))

================================== Ai Message ==================================

**Task decomposition** is the practice of breaking a larger, often complex, piece of work into smaller, more manageable sub‑tasks or components. By dividing a big goal into discrete, well‑defined parts, you make it easier to understand, plan, assign, track, and complete the work.

---

## Why Decompose Tasks?

| Benefit | Explanation |
|---------|-------------|
| **Clarity** | Smaller tasks are easier to describe and understand, reducing ambiguity. |
| **Estimability** | Shorter tasks can be timed and cost‑estimated more accurately. |
| **Parallelism** | Independent subtasks can be worked on concurrently by different people or teams. |
| **Risk reduction** | Problems surface early in small pieces, making them cheaper to fix. |
| **Progress visibility** | Frequent “done” items give a sense of momentum and make tracking easier. |
| **Learning & reuse** | Repeated patterns become visible, enabling templates or libraries of sub‑tasks. |

---

## Core Principles

| Principle | What it means |
|-----------|---------------|
| **Granularity** | Keep sub‑tasks small enough to be completed in a few hours to a few days (often 2‑8 h for agile teams). |
| **Independence** | Aim for tasks that have minimal dependencies on each other; this maximizes parallel work. |
| **Outcome‑focused** | Each sub‑task should produce a tangible deliverable or a clear state change. |
| **Traceability** | Sub‑tasks should map back to a parent goal so you can see how they contribute to the whole. |
| **Testability** | A well‑decomposed task can be validated (e.g., unit‑tested) in isolation. |

---

## Typical Steps to Decompose a Task

1. **Define the overall goal**  
   - Write a concise, outcome‑oriented statement (e.g., “Launch the mobile app’s beta version”).  

2. **Identify major phases or components**  
   - Break the goal into logical high‑level buckets (e.g., “UI design”, “Backend API”, “Beta testing”).  

3. **Drill down within each bucket**  
   - For each bucket, ask: *What concrete steps are needed to finish it?*  
   - Keep asking “What’s the next smaller piece?” until the work item fits the granularity rule.

4. **Validate independence & order**  
   - Sketch a dependency graph; reorder or split further to reduce bottlenecks.  

5. **Assign ownership & estimates**  
   - Attach a responsible person/team and a time/effort estimate to each sub‑task.  

6. **Create acceptance criteria**  
   - Define what “done” looks like for each sub‑task (e.g., “UI mockups approved by product owner”).  

7. **Iterate**  
   - As you progress, you may discover hidden complexities; re‑decompose or merge tasks as needed.

---

## Example: Building a Blog Post Feature

| High‑level Goal | Sub‑tasks (decomposed) |
|-----------------|------------------------|
| **Design UI** | 1. Sketch wireframes for list view<br>2. Review wireframes with stakeholder<br>3. Create high‑fidelity mockups<br>4. Export assets |

Each sub‑task is small enough to be completed in a few hours to a day, has a clear deliverable, and can be assigned to a specific developer or designer.

---

## Where Task Decomposition Is Used

| Domain | Typical Context |
|--------|-----------------|
| **Software development** | Agile user stories → tasks; micro‑service design; CI/CD pipelines |
| **Project management** | Work breakdown structures (WBS) in PMBOK, PRINCE2, etc. |
| **AI prompting / chain‑of‑thought** | Large language models break a request into steps (e.g., “plan → retrieve data → synthesize → format”). |
| **Education & Learning** | Complex assignments are split into research, outline, draft, edit, citation. |
| **Manufacturing / Engineering** | Product design → component design → sub‑assembly → part fabrication. |
| **Business processes** | End‑to‑end workflow mapping (e.g., order‑to‑cash) into discrete activities. |

---

## Tips & Common Pitfalls

| Tip | Why it helps |
|-----|--------------|
| **Start with “Why?”** – Clarify the purpose of the overall goal before chopping it up. | Prevents creating tasks that don’t add value. |
| **Use visual tools** – Flowcharts, Kanban boards, or mind maps make dependencies obvious. | Easier to spot bottlenecks and parallelizable work. |
| **Don’t over‑decompose** – Too many tiny tasks can cause overhead and context‑switching. | Keep a balance; aim for 2‑8 h per task. |
| **Include “glue” tasks** – Integration, documentation, and testing are often forgotten but essential. | Avoids hidden work that later becomes a blocker. |
| **Review regularly** – At sprint planning or milestone reviews, re‑evaluate the decomposition. | Adapts to new information and keeps the plan realistic. |

---

## Quick Checklist for a Well‑Decomposed Task

- [ ] **Specific** – Clear what needs to be done.  
- [ ] **Measurable** – You can tell when it’s finished.  
- [ ] **Achievable** – Reasonable effort for the assigned owner.  
- [ ] **Relevant** – Directly contributes to the parent goal.  
- [ ] **Time‑boxed** – Estimated duration fits the granularity guideline.  

---

### TL;DR

Task decomposition = breaking a big goal into small, independent, outcome‑focused subtasks. It improves clarity, estimation, parallel work, risk management, and progress tracking. Follow a systematic approach (define goal → identify phases → drill down → validate independence → assign & estimate) and keep tasks granular, testable, and traceable to the original objective.

================================== Ai Message ==================================

Common approaches to task decomposition include (1) manual hierarchical breakdowns such as Work‑Breakdown Structures or functional decomposition, where a goal is split into phases, components, and then into small, independent work items; (2) prompt‑based techniques for LLMs—simple “step‑by‑step” prompts (CoT), “what are the sub‑goals?” prompts, or Tree‑of‑Thoughts that generate multiple candidate steps and prune them; and (3) tool‑assisted planning, e.g., translating a problem into PDDL, letting a classical planner produce a plan, and converting that plan back into natural‑language steps. These methods let you create clear, outcome‑focused subtasks that are easier to estimate, assign, and track.

- [ ] **Specific** – Clear what needs to be done.  
- [ ] **Measurable** – You can tell when it’s finished.  
- [ ] **Achievable** – Reasonable effort for the assigned owner.  
- [ ] **Relevant** – Directly contributes to the parent goal.  
- [ ] **Time‑boxed** – Estimated duration fits the granularity guideline.

Task Decomposition#
Chain of thought (CoT; Wei et al. 2022) has become a standard prompting technique for enhancing model performance on complex tasks. The model is instructed to “think step by step” to utilize more test-time computation to decompose hard tasks into smaller and simpler steps. CoT transforms big tasks into multiple manageable tasks and shed lights into an interpretation of the model’s thinking process.
Tree of Thoughts (Yao et al. 2023) extends CoT by exploring multiple reasoning possibilities at each step. It first decomposes the problem into multiple thought steps and generates multiple thoughts per step, creating a tree structure. The search process can be BFS (breadth-first search) or DFS (depth-first search) with each state evaluated by a classifier (via a prompt) or majority vote.

**Standard method for Task Decomposition**

The de‑facto “standard” way to break a complex problem into smaller, tractable pieces for a large language model (LLM) is **Chain‑of‑Thought (CoT) prompting**.  

* **Core idea** – The model is explicitly instructed to “think step‑by‑step” (or “reason through the problem”).  
* **What it does** – The LLM generates a linear sequence of intermediate reasoning steps before producing the final answer.  
* **Why it works** – By forcing the model to allocate more test‑time computation to the problem, CoT lets the model expose latent knowledge, catch mistakes early, and produce more interpretable reasoning traces.  
* **Typical prompt pattern**  

```text
Question: <complex question>
Answer: Let's think step by step.
1. ...
2. ...
...
Final answer: ...
```

CoT has become the baseline for any task‑decomposition work with LLMs because it is simple, model‑agnostic, and consistently improves performance on arithmetic, logic puzzles, commonsense reasoning, and many downstream tasks.

---

## Common extensions of Chain‑of‑Thought

Researchers have built on the basic CoT idea to obtain richer reasoning structures, better exploration, or more reliable answers. Below is a concise catalogue of the most frequently cited extensions (with a one‑sentence description of each).

| Extension | Main contribution / How it extends CoT |
|-----------|----------------------------------------|
| **Tree‑of‑Thoughts (ToT)** – Yao et al., 2023 | Generates **multiple candidate thoughts** at each step, forming a tree; a search algorithm (BFS/DFS) explores the tree and selects the best leaf using a verifier or majority vote. |
| **Least‑to‑Most Prompting** – Zhou et al., 2022 | Decomposes the problem **hierarchically**: first solve the easiest sub‑problem, then use that answer to solve progressively harder sub‑problems, effectively a “bottom‑up” CoT. |
| **Self‑Consistency** – Wang et al., 2022 | Samples many CoT chains (via temperature > 0) and returns the **most frequent final answer**, reducing variance and eliminating outlier reasoning paths. |
| **ReAct (Reason + Act)** – Yao et al., 2023 | Interleaves CoT reasoning with **environmental actions** (e.g., API calls, browsing). The model alternates “Thought:” and “Action:” lines, allowing interactive problem solving. |
| **Reflexion** – Shinn et al., 2023 | After an initial CoT attempt, the model **reflects on mistakes** (via a “self‑critique” prompt) and generates a revised reasoning chain, improving accuracy on hard puzzles. |
| **Decomposed Prompting / Sub‑question Generation** – Liu et al., 2023 | The model first **generates explicit sub‑questions** (or sub‑goals), solves each independently, and finally aggregates the answers—essentially a two‑stage CoT. |
| **Program‑aided Language Models (PAL)** – Gao et al., 2022 | The CoT chain culminates in **syntactically correct code** (e.g., Python) that is executed to obtain the final answer, merging reasoning with external computation. |
| **Plan‑and‑Solve (LLM+P)** – Liu et al., 2023 | Uses a classical planner (PDDL) as an **external planning module**. The LLM translates the problem to PDDL, the planner returns a plan, and the LLM converts it back to natural‑language steps. |
| **Chain‑of‑Thought Prompting with Retrieval** – Borgeaud et al., 2023 | Augments each CoT step with **retrieved documents or facts**, grounding the reasoning in external knowledge. |
| **Iterative Refinement (CoT‑Iter)** – Kojima et al., 2022 | Re‑runs the CoT chain multiple times, each iteration **conditioning on the previous answer**, akin to an inner‑loop refinement. |
| **Meta‑Prompting / Prompt‑Programming** – (various) | Treats the CoT prompt itself as a **programmable template** that can be dynamically assembled (e.g., “If you get stuck, ask for a hint”). |

### Quick visual of the progression

```
CoT (linear chain)
   │
   ├─ Least‑to‑Most (bottom‑up hierarchy)
   ├─ Self‑Consistency (sampling + voting)
   ├─ Reflexion (self‑critique & redo)
   ├─ ReAct (reason ↔ act loop)
   └─ Tree‑of‑Thoughts (branching search)
        └─ Plan‑and‑Solve (external planner as a branch)
```

---

### Take‑away for practitioners

1. **Start with vanilla CoT** – it’s cheap (just a prompt tweak) and yields a solid baseline.  
2. **If you need exploration** – switch to Tree‑of‑Thoughts or Least‑to‑Most.  
3. **If you want robustness** – add Self‑Consistency or Reflexion.  
4. **If your task involves external tools** – use ReAct or Plan‑and‑Solve.  
5. **If you can execute code** – consider PAL to offload arithmetic or logical computation.  

These extensions are widely referenced in the literature and have open‑source implementations in libraries such as **LangChain**, **OpenAI function calling**, **AutoGPT**, and the **LLM‑Agents** toolkit, making them easy to plug into existing pipelines.
